# API-контракт: Mini Issue Tracker

Документ описує HTTP API для ЛР2 і майбутніх тестів ЛР3. Бізнес-правила, поля й помилки не повторюються: їх єдине джерело істини [requirements.md](requirements.md). Тут для кожної операції визначено маршрут, вхід, успішну відповідь і коди помилок, а за правилами є посилання.

## 1. Загальні домовленості

- Формат обміну: JSON (`Content-Type: application/json`), кодування UTF-8. Назви полів збігаються з розділом «Модель даних» у requirements.md.
- Тіло запиту, яке не є коректним JSON-об'єктом (зокрема масив, число, невалідний JSON), дає помилку валідації. Для `PATCH /issues/{id}` така перевірка іде після перевірки існування й стану заявки, як і решта перевірок тіла.
- Дата й час (`created_at`): ISO 8601 у UTC із суфіксом `Z`, наприклад `2026-10-29T10:15:00Z` (D-11).
- Ідентифікатор у шляху (`{id}`): якщо він не додатне ціле число (наприклад, `abc` або `0`), це відповідь «не знайдено» для будь-якого маршруту з `{id}` (D-10).
- Автентифікації немає. Ідентифікатори користувачів 1 і 2 лише позначають виконавця й автора коментаря.

### 1.1. Коди результатів

Єдина відповідність категорій результатів із requirements.md (розділ «Каталог результатів і помилкових ситуацій») і HTTP-кодів. Для однієї категорії завжди той самий код.

| Категорія | HTTP-код |
|---|---|
| Успішне читання, успішна зміна, успіх без змін, порожній результат | 200 |
| Успішне створення (заявка, коментар) | 201 |
| Не знайдено | 404 |
| Конфлікт зі станом | 409 |
| Помилка валідації | 422 |

Порядок перевірок, коли запит порушує кілька правил, визначає requirements.md («Пріоритет перевірок» і «Порядок перевірки» PATCH): не знайдено, потім конфлікт, потім валідація. Реалізація має його дотримуватися (див. architecture.md). Єдиний виняток описаний для зміни статусу (3.7): невідоме значення статусу перевіряється до переходу.

Обґрунтування кодів (за семантикою HTTP, MDN): `404`: запитаного ресурсу не існує; `409`: запит коректний за формою, але суперечить поточному стану ресурсу (наприклад, повернення закритої заявки в `OPEN`); `422`: запит розпізнаний, але його дані не відповідають правилам. Розмежування саме цих трьох кодів є навчальною конвенцією ЛР1.

### 1.2. Формат помилки

Усі помилки мають однакову структуру. Поле `details` є лише для помилки валідації.

```json
{
  "error": {
    "type": "validation_error",
    "message": "Запит містить некоректні дані",
    "details": [
      { "field": "title", "reason": "довжина після видалення крайніх пробілів має бути від 3 до 120 символів" }
    ]
  }
}
```

| Значення `type` | HTTP-код |
|---|---|
| `not_found` | 404 |
| `conflict` | 409 |
| `validation_error` | 422 |

### 1.3. Об'єкти відповіді

**Issue:** `id`, `title`, `description`, `status`, `priority`, `assignee_id` (ціле або `null`), `created_at`.

**Comment:** `id`, `issue_id`, `author_id`, `text`, `created_at`.

**User:** `id`, `name`.

## 2. Огляд маршрутів

| # | Метод і шлях | Призначення | Успіх | Помилки | Вимога |
|---|---|---|---|---|---|
| 1 | `GET /health` | Перевірка запуску | 200 | - | NFR-04 |
| 2 | `GET /users` | Два тестові користувачі | 200 | - | FR-05, FR-06 |
| 3 | `POST /issues` | Створити заявку | 201 | 422 | FR-01, US-01 |
| 4 | `GET /issues` | Список із фільтрами | 200 | 422 | FR-02, US-02 |
| 5 | `GET /issues/{id}` | Одна заявка | 200 | 404 | FR-02, US-02 |
| 6 | `PATCH /issues/{id}` | Часткове редагування | 200 | 404, 409, 422 | FR-03, FR-05, US-03, US-05 |
| 7 | `PATCH /issues/{id}/status` | Зміна статусу | 200 | 404, 409, 422 | FR-04, US-04 |
| 8 | `POST /issues/{id}/comments` | Додати коментар | 201 | 404, 422 | FR-06, US-06 |
| 9 | `GET /issues/{id}/comments` | Список коментарів | 200 | 404 | FR-06, US-06 |

## 3. Опис операцій

### 3.1. `GET /health`

Технічна перевірка запуску. Дані не читає і не змінює.

**Успіх, 200:**

```json
{ "status": "ok" }
```

### 3.2. `GET /users`

Повертає довідник користувачів, за зростанням `id`.

**Приклад запиту:** `GET /users`

**Успіх, 200:**

```json
[
  { "id": 1, "name": "Agent A" },
  { "id": 2, "name": "Agent B" }
]
```

### 3.3. `POST /issues`

Створює заявку. Правила полів: розділ «Модель даних» requirements.md.

**Тіло запиту:**

| Поле | Обов'язкове | Примітка |
|---|---|---|
| `title` | так | межі й нормалізація за моделлю даних, D-04 |
| `description` | ні | типове `""` |
| `priority` | ні | типове `medium` |

Інші поля (`id`, `status`, `assignee_id`, `created_at` та невідомі) недозволені й дають 422 (D-05).

**Успіх, 201.** Повертається створена заявка зі статусом `OPEN`, `assignee_id: null`.

**Помилки:**

| Код | Коли |
|---|---|
| 422 | назва поза межами, відсутня або не рядок; опис довший за 2000 символів; недозволене значення `priority`; недозволене або невідоме поле |

**Приклад запиту:**

```json
{ "title": "Помилка входу", "priority": "high" }
```

**Приклад відповіді, 201:**

```json
{
  "id": 1,
  "title": "Помилка входу",
  "description": "",
  "status": "OPEN",
  "priority": "high",
  "assignee_id": null,
  "created_at": "2026-10-29T10:15:00Z"
}
```

**Приклад помилки.** Запит `{ "title": "ab" }`, відповідь 422:

```json
{
  "error": {
    "type": "validation_error",
    "message": "Запит містить некоректні дані",
    "details": [
      { "field": "title", "reason": "довжина після видалення крайніх пробілів має бути від 3 до 120 символів" }
    ]
  }
}
```

### 3.4. `GET /issues`

Повертає список заявок у порядку створення (D-03).

**Параметри запиту (необов'язкові):**

| Параметр | Допустимі значення |
|---|---|
| `status` | `OPEN`, `IN_PROGRESS`, `CLOSED` |
| `priority` | `low`, `medium`, `high` |

Якщо задано обидва, діє логічне AND (FR-02). Значення, які не входять до допустимих (зокрема порожній рядок), дають 422 (D-09). Невідомі параметри запиту ігноруються.

**Успіх, 200.** Масив заявок; якщо збігів немає, порожній масив `[]`.

**Помилки:**

| Код | Коли |
|---|---|
| 422 | недозволене значення `status` або `priority` у параметрах |

**Приклад запиту:** `GET /issues?status=OPEN&priority=high`

**Приклад відповіді, 200:**

```json
[
  {
    "id": 1,
    "title": "Помилка входу",
    "description": "",
    "status": "OPEN",
    "priority": "high",
    "assignee_id": null,
    "created_at": "2026-10-29T10:15:00Z"
  }
]
```

### 3.5. `GET /issues/{id}`

Повертає одну заявку.

**Успіх, 200.** Об'єкт Issue.

**Помилки:**

| Код | Коли |
|---|---|
| 404 | заявки немає або `{id}` не додатне ціле (D-10) |

**Приклад запиту:** `GET /issues/1`

**Приклад відповіді, 200:**

```json
{
  "id": 1,
  "title": "Помилка входу",
  "description": "",
  "status": "OPEN",
  "priority": "high",
  "assignee_id": null,
  "created_at": "2026-10-29T10:15:00Z"
}
```

**Приклад помилки.** `GET /issues/99`, відповідь 404:

```json
{
  "error": {
    "type": "not_found",
    "message": "Заявку з id 99 не знайдено"
  }
}
```

### 3.6. `PATCH /issues/{id}`

Часткове редагування. Усі правила (відсутнє поле і `null`, порожній запит, невідоме поле, атомарність, порядок перевірки) визначені в розділі «Правила часткового редагування (PATCH)» requirements.md і тут не дублюються.

**Тіло запиту:** будь-яка непорожня підмножина полів `title`, `description`, `priority`, `assignee_id`. Для зняття виконавця передається `"assignee_id": null`. Поле `status` недозволене (для нього окремий маршрут 3.7).

**Успіх, 200.** Повертається повна оновлена заявка (також коли передане значення збігається з поточним).

**Помилки:**

| Код | Коли |
|---|---|
| 404 | заявки немає або `{id}` не додатне ціле |
| 409 | заявка має статус `CLOSED` (будь-який PATCH, також порожній; D-01) |
| 422 | порожнє тіло (незакрита заявка, D-08); недозволене або невідоме поле; `null` для поля, що його не допускає; некоректне значення, довжина чи тип |

**Приклад запиту** (призначення виконавця): `PATCH /issues/1`

```json
{ "assignee_id": 2 }
```

**Приклад відповіді, 200:**

```json
{
  "id": 1,
  "title": "Помилка входу",
  "description": "",
  "status": "OPEN",
  "priority": "high",
  "assignee_id": 2,
  "created_at": "2026-10-29T10:15:00Z"
}
```

**Приклад помилки.** Заявка `1` закрита, запит `{ "priority": "low" }`, відповідь 409:

```json
{
  "error": {
    "type": "conflict",
    "message": "Заявка закрита, її дані не можна змінювати"
  }
}
```

### 3.7. `PATCH /issues/{id}/status`

Окрема операція зміни статусу. Дозволені, заборонені переходи й повторне встановлення статусу визначає матриця переходів у requirements.md («Життєвий цикл заявки»), D-07.

**Тіло запиту:**

| Поле | Обов'язкове | Примітка |
|---|---|---|
| `status` | так | `OPEN`, `IN_PROGRESS` або `CLOSED` |

Інші поля та відсутнє або `null` значення `status` дають 422.

**Успіх, 200.** Повертається заявка з новим статусом. Для переходу «уже встановлений» також 200, заявка не змінена.

**Помилки:**

| Код | Коли |
|---|---|
| 404 | заявки немає або `{id}` не додатне ціле |
| 409 | заборонений перехід (`IN_PROGRESS` → `OPEN`, `CLOSED` → `OPEN`, `CLOSED` → `IN_PROGRESS`) |
| 422 | відсутній, `null` або невідомий `status` (наприклад, `DONE`); невідоме поле |

Спочатку перевіряється, що значення є одним з трьох статусів (422), потім дозволеність переходу (409).

**Приклад запиту:** `PATCH /issues/1/status`

```json
{ "status": "IN_PROGRESS" }
```

**Приклад відповіді, 200:**

```json
{
  "id": 1,
  "title": "Помилка входу",
  "description": "",
  "status": "IN_PROGRESS",
  "priority": "high",
  "assignee_id": 2,
  "created_at": "2026-10-29T10:15:00Z"
}
```

**Приклад помилки.** Заявка `1` має статус `CLOSED`, запит `{ "status": "OPEN" }`, відповідь 409:

```json
{
  "error": {
    "type": "conflict",
    "message": "Перехід зі статусу CLOSED у статус OPEN заборонений"
  }
}
```

### 3.8. `POST /issues/{id}/comments`

Додає коментар до наявної заявки. Дозволено і для закритої заявки (requirements.md, «Операції для закритої заявки»).

**Тіло запиту:**

| Поле | Обов'язкове | Примітка |
|---|---|---|
| `author_id` | так | 1 або 2 |
| `text` | так | 1–1000 символів після видалення крайніх пробілів, D-06 |

`issue_id` береться зі шляху, у тілі не передається. Інші поля дають 422.

**Успіх, 201.** Повертається створений коментар.

**Помилки:**

| Код | Коли |
|---|---|
| 404 | заявки немає або `{id}` не додатне ціле |
| 422 | порожній текст або лише з пробілів; текст довший за 1000 символів; `author_id` не 1 і не 2; відсутнє поле; невідоме поле |

Якщо заявки немає, а тіло також некоректне, відповідь 404 (порядок перевірок).

**Приклад запиту:** `POST /issues/1/comments`

```json
{ "author_id": 1, "text": "Відтворюється на версії 2.1" }
```

**Приклад відповіді, 201:**

```json
{
  "id": 1,
  "issue_id": 1,
  "author_id": 1,
  "text": "Відтворюється на версії 2.1",
  "created_at": "2026-10-29T10:20:00Z"
}
```

**Приклад помилки.** Запит `{ "author_id": 3, "text": "Привіт" }`, відповідь 422:

```json
{
  "error": {
    "type": "validation_error",
    "message": "Запит містить некоректні дані",
    "details": [
      { "field": "author_id", "reason": "допустимі значення: 1 або 2" }
    ]
  }
}
```

### 3.9. `GET /issues/{id}/comments`

Повертає коментарі заявки в порядку створення (D-03).

**Успіх, 200.** Масив Comment; якщо коментарів ще немає, порожній масив `[]`.

**Помилки:**

| Код | Коли |
|---|---|
| 404 | заявки немає або `{id}` не додатне ціле |

**Приклад відповіді, 200:**

```json
[
  {
    "id": 1,
    "issue_id": 1,
    "author_id": 1,
    "text": "Відтворюється на версії 2.1",
    "created_at": "2026-10-29T10:20:00Z"
  }
]
```
