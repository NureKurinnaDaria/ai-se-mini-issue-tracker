## 5. Виправлення

### 5.1. M1: повторне відкриття CLOSED (Skill v1, зріз B)

- Симптом: `PATCH /issues/{id}/status` зі статусом `OPEN` для закритої заявки дає 200, повторний GET показує `OPEN`.
- FR/AC: FR-04, AC-04.3, AC-04.4.
- Моя гіпотеза (до звернення до AI): у `_TRANSITIONS` для `CLOSED` дозволено `OPEN`, тому перевірка в `change_status` пропускає перехід; логіка правильна, помилка в даних.
- Висновок AI: збігається з гіпотезою; зіставлено матрицю коду з матрицею `requirements.md`. Він назвав прочитаним розділ «Каталог результатів», якого я не передавала; на висновок це не вплинуло.
- Skill: `tracker-slice` v1 з `lab02-implemented`, зріз B, режим чату. Skill вимагав план до коду: AI назвав зріз, прочитані розділи, перевірки й план, чекав підтвердження, не стверджував, що тести пройшли.
- Патч (`70bfd9c`): один рядок, `"CLOSED": {"CLOSED", "OPEN"}` → `"CLOSED": {"CLOSED"}` (`reports/lr3/m1-fix.diff`).
- Результат: ті самі T10 і повний T1 проходять (252 passed двічі, ruff чистий).

### 5.2. M3: назва заявки (зріз A)

- Симптом: `POST /issues` з назвою `O'Brien` дає помилку сервера; `Save button` зберігається.
- FR/AC: FR-01, AC-01.1; правило «SQL лише параметризований».
- Гіпотеза: у `insert_issue` `title` вставлено в текст SQL f-рядком, апостроф закриває літерал.
- Висновок AI: збігається; той самий рядок дає B608.
- Skill: `tracker-slice` v1, зріз A (`database.py` у переліку файлів зрізу є), режим чату.
- Патч (`f6dc320`): `?` замість `'{title}'`, `title` у кортежі параметрів (`reports/lr3/m3-fix.diff`).
- Результат: обидва тести з апострофом проходять, повний T1 252 passed, ruff чистий, Bandit 0 повідомлень.
- Примітка: на M3 `x'; DROP TABLE issues; --` завершилось помилкою SQLite, а не втратою таблиці, бо `sqlite3.execute` виконує один оператор. Тест доводить дефект зв'язування, а не успішну ін'єкцію.

### 5.3. M2: частковий PATCH (лише діагностика)

Заявка відкрита, `priority=medium`, `assignee_id=1`; запит `PATCH` з `{"priority": "high", "assignee_id": 999}`.

|                                | R0       | M2     |
| ------------------------------ | -------- | ------ |
| Відповідь                      | 422      | 422    |
| `priority` у повторному GET    | `medium` | `high` |
| `assignee_id` у повторному GET | `1`      | `1`    |

Код 422 сам не доводить, що дані не змінились, тому тест порівнює повний `snapshot` до запиту й після. На R0 `update_issue` у `service.py` спершу повністю валідує тіло (зокрема допустимого виконавця), обчислює підсумкові значення й записує їх одним `UPDATE` в одній транзакції; поки валідація не завершилась, запису немає. Альтернатива: записувати поля поступово в одній транзакції й відкотити її при помилці. У M2 частина полів пишеться до перевірки виконавця.
